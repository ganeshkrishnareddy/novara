# NOVARA — product handover

This is the handover for the local NOVARA build in `D:\NOVARA`. It records how
to run the product, what is implemented and verified, and what remains. All
counts are derived from `docs/FEATURE_PARITY/MASTER_FEATURE_MATRIX.csv` and are
regenerated by `docs/FEATURE_PARITY/generate_deliverables.py` — none are
hand-set. "Local" means this machine only: no deployment, publish, external
message or Git write is part of this handover.

## 1. Run the product

Windows PowerShell:

```powershell
cd D:\NOVARA
.\scripts\start-local.ps1
```

Then open <http://localhost:8000>. The API docs are at
<http://localhost:8000/docs>. Finish first-run setup in the browser. No
Docker, PostgreSQL, Redis, hosted account, API key or licence is required for
local use.

The same build can be started with `sh scripts/start-local.sh` on macOS/Linux.
Container definitions exist in `Dockerfile` and `docker-compose.yml` but are
**not verified here** — container tooling is unavailable in this environment.

## 2. What the product is

NOVARA is one self-hostable business operating system with a single identity,
workspace, permission, event, notification, search and audit spine — not ten
separate apps. The working web app has 24 views: dashboard, search, insights,
contacts, companies, leads, deals, inbox, tasks, projects, documents,
campaigns, surveys, notifications, activity, drafts, agents, jobs, adapters,
operations, integrations, workspaces, profile and settings.

Backend capability modules (23): sales, CRM intelligence, marketing, email
campaigns, support, feedback, analytics, feature flags, search, projects,
documents, document links, storage, automation, notification preferences,
agents, integrations, jobs, adapters, operations, workspace administration,
native API resources and the core workflow engine.

The core workflow runs end to end locally: website form → one CRM contact →
lead → task → notification → outreach **draft** → authorised approval → audit
events. NOVARA never sends an external message from its core service. Adapters
are local mocks with `delivered: false` unless real credentials are configured
and an external effect is explicitly authorised — which has not happened.

## 5. Decisions taken for this build

- Work stays local. No Git write, deployment, public publishing, outbound
  integration delivery, purchase or irreversible external action.
- Clean-room implementations only. No source copied from the ten reference
  repositories; licence decisions are in `docs/research/LICENSE_COMPLIANCE.md`.
- No real provider credentials were used. Email/WhatsApp/SMS/AI adapters remain
  explicit local mocks until the owner supplies credentials and authorises
  outbound effects through a secret process.
- Light theme only. No placeholder data is presented as live business data.
- New capability tables are created idempotently so a local dev database and a
  fresh database converge.

## 6. Owner decisions still required before any release

1. Choose NOVARA's own licence, trademark and production domain (blockers
   B-03/B-04).
2. Choose production infrastructure and exercise the Docker/PostgreSQL path on
   the target host; only SQLite is verified here (B-01/B-12).
3. Authorise deployment explicitly. Nothing has been deployed.
4. Decide whether real outbound integrations are wanted and supply credentials
   through a secret process (B-07).
5. Complete commercial/legal sign-off (pricing, terms, privacy, data handling).
6. Arrange real tablet/mobile device testing; only static responsive review
   has been done (B-11).
7. Platform signing, notarisation and store credentials for signed installers
   (B-06/B-08).
